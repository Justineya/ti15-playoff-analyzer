1. 我的看法

这件事值不值得做成站

值。TI 淘汰赛窗口只有四天，信息密度极高：队名改了、瑞士赛刚打完、BP 会按对手变、Bo3/Bo5 的盘口逻辑完全不同。靠每次打开 Cursor 问一遍，时效和对齐成本都太高。做成站的核心价值是同一套数据 + 同一套模型，赛程更新后刷新，而不是重写文章。

不要做成第二个液体百科

Liquipedia 已经把赛程、阵容、比分、英雄统计做得很好。我们不该再做一个百科。差异化在后半段：交手画像 → 英雄池/禁用倾向 → 模拟 BP → 系列胜率 → 竞猜决策。百科给事实，我们给「这场该怎么下判断」。

竞猜：市场一层、模型一层

系列胜率先挂 Polymarket 赛前隐含概率（市场共识，不是我们的模型）。旁边再放本届八强样本算出来的倾向。首十杀、地图分、让分分开写。不爬私盘，不写「稳胆」。缺数据就标缺，不编。

队名仍要合并，但不再回溯赛季

PARIVISION → TEAM VISION，BetBoom → BoomBoys，Tundra → 1w → Iron Wing。主键仍是 team_id。合并只为了对上本届 TI 的场次，不把改名之前一年的外战拉进来。

1c. 和另一套做法怎么对齐

你贴的那套数据哲学大部分采用。差在两处：样本更窄；首十杀不必靠人工看录像。

另一套说法我们怎么做
Liquipedia 当赛程/比分/名单/晋级的基准采用。主页面已核对，parse 需 Gzip。
Dota2 Pro Tracker / Dotabuff 交叉核对 BP 和时长采用核对思路。注意这是两个站：Dotabuff 是百科级职业页；D2PT 是 7.41e 高分 Meta。比赛级交叉我们用 OpenDota，不爬 D2PT。
Polymarket 赛前 BO3 系列隐含概率采用。公开 API 已拉到 8/20 四场（见下方对阵卡）。这是市场共识，不当成模型胜率。
Oddsportal 做盘口交叉可选人工对照。产品不接博彩聚合站爬虫。
F10K 无官方字段，大量标【无公开存档】「不是官方字段」对。解析场可以从击杀时间轴算出哪边先堆到 10 杀。不是看谁收第 10 刀。
少数局靠直播时间轴人工摘 F10K只留给未解析场。优先 POST OpenDota parse；仍没有才标缺失。

2. 产品长什么样

一个站点，三个使用节奏：赛前看预览、赛中看 BP 对照、赛后看模型校准。

01

总览 / 对阵图

双败图、下一场倒计时、瑞士成绩与晋级路径。点一场进入系列页。

02

系列预览页

每场核心页。本届 H2H（没有就写无交手）、TI15 英雄池、模拟 BP、Polymarket 系列概率、F10K 本届倾向、竞猜卡。

03

队伍 / 选手页

只画这 80 局：位置英雄池、一三楼/禁用、F10K 得失、时长分布。不混外战。

04

版本 Meta 层

7.41e 职业优先度、本届 TI 禁用率、和「这支队会不会拿」分开显示。

05

竞猜面板

系列胜者（市场 vs 本届样本）、地图分 / 让分、F10K 倾向。信心低标「过」。缺解析就标缺失。

06

赛后复盘

真实 BP vs 模拟 BP、预测 vs 结果、校准曲线。没有这一页，模型会一直自我感觉良好。

3. 数据接口：液体百科能不能用？

液体百科管事实。OpenDota 管这 80 局怎么打、以及 F10K 推导。Polymarket 管赛前市场共识。

L1 赛程事实

Liquipedia（液体百科）

  • 对阵图、开赛时间、阵容、转会、队名变更、VOD
  • 本届页面：The International/2026
  • Steam leagueid 已写在 infobox 里：19719

官方 REST v3（api.liquipedia.net/api/v3）要申请 API Key，结构化最好。没有 Key 时，MediaWiki action=parse 可以拉 wikitext，但必须带 Gzip 和合规 User-Agent，否则直接 406。

L2 比赛细节 · 已打通

OpenDota

  • 免费 REST，无需 Key 即可读公开职业数据
  • /leagues/19719/matches：本届已入库 100+ 场
  • /teams/{id}/heroes、/players/{id}/heroes：英雄池
  • /explorer：SQL 聚合 H2H、BP、时长、经济差

P1 主力。只拉八强出场的 80 局。队名会空，必须用 team_id。

L3 赛前系列胜率 · 已打通

Polymarket（预测市场，不是模型）

  • 公开 Gamma API，无需 Key
  • 已接到 8/20 四场 BO3 系列盘、G1 胜者、O/U 2.5、让分 1.5
  • 冠军盘也可做八强夺冠对照（VISION 约 38%）

取开赛前流动性稳定后的隐含概率，标注抓取时间。这是市场共识 ≠ 我们的预测。目前这四场 没有 F10K 盘口，所以赛前首十杀不能假装来自 Polymarket。

L4 首十杀 · 可计算

F10K = 从击杀时间轴推导

  • Valve / 液体百科原生都没有这个字段，另一套提醒是对的
  • 定义钉死：哪支队伍先获得 10 次英雄击杀，不是全局第 10 刀的收刀人
  • OpenDota 解析场：按时间累加两边人头，谁先到 10 谁赢这项
  • 脚本：scripts/f10k.py <match_id>，已在本届对局跑通

同一秒两记击杀会标「时序歧义」，不强行判。未解析场先请求 parse；仍没有才写【无存档】——这是真缺失，不是偷懒。不编 F10K。

L5 加深 · 可选

STRATZ GraphQL

  • Replay 级：分路、视野、物品时序、Draft 顺序
  • 适合 BP 模拟和「赛况怎么打崩」
  • 需要 API Token，且有 Cloudflare 门

第二期再接。没有它，BP 模拟只能用「谁常拿 / 谁常禁 / 版本优先度」，做不到真实先后手建模。

L6 人工对照

Dotabuff ≠ Dota2ProTracker

  • Dotabuff：职业赛页，Polymarket 冠军盘的官方结算源之一
  • D2PT：7.41e 高分/职业 Meta，无稳定公开 API，不爬
  • 液体百科赛果延迟时，用 OpenDota / Dotabuff 交叉，不把 D2PT 当赛果源

另一套把「Dota 2 Pro Tracker（DOTABUFF 职业赛事模块）」写在一起了。产品里拆开，避免对不上。

5. 分析引擎怎么做（你点的那几项）

  1. 历史战绩（仅本届）

    只看这 80 局。八强在瑞士轮已经有多组交手（VISION–Falcons、VISION–BoomBoys、VISION–Spirit、Liquid–Yandex、Liquid–Spirit、Liquid–IW、IW–NGX、IW–BB、IW–Falcons、IW–Yandex、Falcons–BB、NGX–Spirit）。没有交手就写「本届无 H2H」，不拿去年 TI 或 ESL 来凑。

  2. 常用英雄

    只统计这 80 局里的 pick/ban/位置。输出「本届拿过」「本届被针对禁用」。不混生涯签名英雄——版本是 7.41e，外战会污染 BP。

  3. 逐场四镜头（已上线）

    每局固定写：BP；节奏；前中期攻防；哪边先到 10 杀、中单参与了几次（击杀+助攻）；中辅合计参与。详见 逐场分析。

  4. 胜率：市场一行、样本一行

    第一行 Polymarket BO3 隐含概率（标注时间）。第二行用这 80 局的胜负/地图分/F10K 做收缩估计。分歧大就降信心。不把市场价改写成「我们预测 51.2%」。

  5. 赛况模拟

    只用本届时长、经济曲线、F10K 后 10 分钟的走向。三条路径：对线滚雪球、中期打架、超长发育。本届平均时长偏高，拖局要单独标。

  6. 竞猜卡

    每场五格：系列（跟/不跟市场）、地图分或 O/U 2.5、让分是否覆盖、F10K 倾向（仅当样本够）、信心。F10K 没有赛前市场时，只给本届经验倾向并标明「非盘口」。缺数据就【无存档】，不编。

6. 部署形态

推荐架构

静态前端（这个目录就能先挂 GitHub Pages / Cloudflare Pages）+ 一个很薄的数据刷新脚本。TI 这四天用定时拉取 OpenDota + Liquipedia parse，写成 JSON，前端只读本地数据。这样你打开的是网页，不是 Cursor。

为什么第一期不上重后端

淘汰赛一共就十几场系列。数据量小，缓存 JSON 足够。等 STRATZ Token、Liquipedia v3 Key 齐了，再加 API 层也不迟。先保证 8/20 能看四场预览。

Liquipedia parse / OpenDota REST
        ↓  定时脚本（每 15–30 分钟）
     data/*.json  （对阵、80 局样本、F10K、Poly 盘口、模型输出）
        ↓
   静态网页  ← 你每天打开的就是这个
